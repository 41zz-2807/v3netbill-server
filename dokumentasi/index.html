Dokumentasi v3Netbill — versi 1.0

Ringkasan & Arsitektur

v3Netbill adalah sistem penagihan untuk warnet (komputer bersama). Pelanggan membayar sesuai waktu pemakaian; kasir mengatur semuanya lewat web atau HP; tiap komputer kasir menjalankan agent Windows yang mengunci layar sampai pelanggan membayar dan masuk.

Satu kalimat cara kerjanya

Pelanggan membayar → kasir membuat voucher atau member → pelanggan mengetik kodenya di layar kunci PC → agent mengunci Task Manager dan mulai menghitung mundur → server memotong saldo tiap detik → saat waktu habis atau kasir menekan Kunci, layar kembali terkunci dan sisa dikembalikan.

Empat aplikasi yang membentuk sistem

1. Frontend — Web

TypeScript · React 19 · Vite 8 · Tailwind CSS 4

Halaman yang dibuka kasir & admin lewat peramban. Dashboard, PC Management, Voucher & Member, Transaksi, Laporan, Pengaturan.

Port dev 5173 · hasil build disajikan backend di port 3000.

2. Backend — API

TypeScript · NestJS 12 (ESM) · Prisma 5.22 · PostgreSQL 15

Otak sistem. Menyediakan REST API, WebSocket real-time, cron, PDF, email, Telegram, dan push FCM. Server adalah satu-satunya sumber kebenaran waktu & tagihan.

Port 3000 · WebSocket namespace /session.

3. Mobile — Android

Dart 3 · Flutter 3.44.4

Aplikasi HP untuk kasir. Fungsi yang sama dengan web, dibuat untuk dipakai sambil berjalan di warnet. Bottom navigation: Home, Voucher, Profile.

Format APK · bisa memperbarui dirinya sendiri tanpa peramban.

4. Agent — Windows

C# · .NET 8 · WPF · WiX 4.0.5 (MSI)

Berjalan di setiap PC kasir. Dua bagian: Service (tanpa jendela, penghubung server) dan Overlay (jendela layar kunci fullscreen yang dilihat pelanggan).

Install · bisa memperbarui dirinya sendiri per-PC.

Semua kode memakai huruf Indonesia dalam UI Istilah teknis (nama tabel, endpoint, perintah) tetap dalam bahasa Inggris supaya cocok dengan kode dan dokumentasi asli. Nama PC, kode voucher, dan nama member bebas & tidak boleh diubah sembarangan — sebagian dari keduanya adalah kredensial login.

Kenapa backend menyajikan halaman web-nya sendiri

Domain publik diarahkan ke port 3000 (backend), bukan ke port 5173. Backend memakai ServeStaticModule untuk menyajikan hasil build frontend. Konsekuensinya ada satu proses saja yang perlu dijaga, dan tidak ada proxy di depan — Cloudflare Tunnel sudah cukup untuk meneruskan ke satu port itu.

Dua aturan yang sering dilanggar
  1. Jangan menaruh berkas sensitif di frontend/dist. Folder itu disajikan tanpa autentikasi. Hanya /api, /session, dan /socket.io yang dikecualikan.
  2. Cara deploy frontend yang benar adalah docker compose exec v3netbill-frontend npm run build — bukan docker compose up -d --build v3netbill-backend, karena folder dist di-bind mount dan hasil build di dalam image tidak pernah dibaca.

Kenapa Teknisi dan SesiTeknisi berdiri sendiri Ini keputusan desain, bukan sekadar pilihan teknis:
  1. Session.accountId punya FK RESTRICT yang tidak boleh null. Memaksakan teknisi lewat Account berarti mengubah skema jalur yang sedang menagih pelanggan.
  2. Account selalu menghasilkan Transaction dan Session yang ikut rekap pendapatan. Teknisi justru harus tidak masuk hitungan itu.
  3. Account.nama adalah kredensial login pelanggan dan ikut tampil di daftar akun — tidak pantas dipakai untuk kredensial teknisi.

Bedakan VOUCHER dan MEMBER

Voucher punya kodeUnik (6 angka) dan tidak punya nama. Kadaluwarsa kalau >30 hari tidak dipakai.

Member tidak punya kodeUnik sama sekali — yang dipakai login adalah kolom nama. Nama itu jadi kredensial, jadi panjangnya dibatasi 4–40 karakter.

Password awal semua akun baru = 0000 (bukan acak). Pelanggan menggantinya sendiri dari layar PC.

Sesi yang sedang berjalan
SELECT s.id, p."namaPc", a."kodeUnik", a."nama", s."durasiTerpakaiDetik"
  FROM "Session" s
  JOIN "Pc" p ON p.id = s."pcId"
  JOIN "Account" a ON a.id = s."accountId"
 WHERE s.status = 'BERJALAN';
PC yang heartbeat-nya basi (>> 30 detik)
SELECT "namaPc", "status", "lastHeartbeatAt",
       EXTRACT(EPOCH FROM (now() - "lastHeartbeatAt"))::int AS detik_lalu
  FROM "Pc"
 WHERE "lastHeartbeatAt" IS NULL
    OR "lastHeartbeatAt" < now() - interval '30 seconds'
 ORDER BY "lastHeartbeatAt" NULLS FIRST;

Urutan hapus data itu penting Karena Transaction.accountId dan Session.accountId punya ON DELETE RESTRICT, menghapus Account duluan akan ditolak PostgreSQL. Urutan yang benar: Transaction → Session → Account. User tidak boleh dihapus selama masih ada transaksinya.

Contoh query berguna

Laporan pendapatan sederhana dari query langsung
SELECT date_trunc('day', "createdAt") AS hari,
       SUM("nominal")  AS pendapatan,
       COUNT(*)        AS jumlah_transaksi
  FROM "Transaction"
 WHERE "dibatalkan" IS NULL
   AND "createdAt" >= now() - interval '7 days'
 GROUP BY 1
 ORDER BY 1 DESC;
Saldo seluruh member aktif
SELECT COUNT(*) AS jml_member,
       SUM("sisaWaktuDetik") / 3600.0 AS total_jam,

Setiap 10 detik backend memeriksa PC yang idle. Pengamannya, urutannya wajib:

Kalau agent offline, timer HARUS dibiarkan menyala Kalau tetap diset null karena “sudah dikirim”, PC itu menggantung menyala selamanya — tidak ada perintah kedua yang akan dikirim.

Status PC: sumber kebenaran bukan kolom database

statusPcDitampilkan()
sesi dalam masa tenggang (< grace_period_detik)  -> ACTIVE
heartbeat basi (> 30 detik, atau null)           -> OFFLINE
heartbeat segar + ada sesi berjalan               -> ACTIVE
selain itu                                         -> nilai kolom

AMBANG_OFFLINE_MS = 30_000   (heartbeat agent tiap 15 detik)
Kolom Pc.status adalah cache Kolom itu boleh berisi OFFLINE di database — itu normal, bukan data rusak. Sumber kebenaran hanya dua: lastHeartbeatAt dan Session berstatus BERJALAN.
Masa tenggang juga menahan status PC Sesi yang agentnya sempat terputus tidak langsung dimatikan — server menunggu grace_period_detik (bawaan 180 detik) sebelum menghentikannya dengan alasan disconnect_timeout. Selama itu, PC tetap ditampilkan ACTIVE, bukan OFFLINE.

Kenapa perlu begitu: kalau tidak, satu kedipan jaringan atau satu restart server membuat seluruh PC di warnet terlihat mati selama hampir tiga menit, padahal sesi pelanggan masih berjalan dan masih ditagih. Setelah masa tenggang lewat, aturan lama berlaku lagi — heartbeat basi menang dan PC ditampilkan OFFLINE.

Kalau fiturnya dimatikan lewat grace_period_detik = 0, tidak ada yang ditahan dan PC langsung kembali OFFLINE begitu heartbeat basi.

Alur sekarang
401 + request membawa token
  -> _loginUlangOtomatis()   (pakai kredensial tersimpan)
       berhasil  -> ulang request ASLINYA tepat SEKALI
       gagal     -> clear + onUnauthorized() seperti semula

Tiga penjaga yang wajib: (1) login ulang memakai _dio.post langsung, bukan post() — kalau lewat post() berarti lewat guard lagi dan loop tanpa akhir; (2) flag sudahCobaLoginUlang supaya request hanya diulang sekali; (3) flag _sedangLoginUlang supaya puluhan login ulang tidak berbarengan.

Trade-off yang sengaja dipilih: password disimpan apa adanya Supaya login ulang otomatis bisa jalan, password disimpan di flutter_secure_storage. Alternatif yang lebih aman (perpanjang umur JWT di backend) ditawarkan, tapi user memilih opsi ini.

Jebakan -d yang paling merusak

Yang benar
# CI meneruskan:
  -d SERVER_URL="${{ env.SERVER_URL }}"

# Product.wxs harus dikonsumsi sebagai preprocessor variable:
  <Property Id="SERVER_URL" Value="$(var.SERVER_URL)" />

Kalau Value ditulis literal (Value="http://localhost:3000"), define-nya tidak pernah terpakai — agent terpasang lalu mencoba konek ke localhost di PC-nya sendiri. Gejalanya: semua PC jadi OFFLINE, wallpaper tidak pernah berubah, dan log server tidak menunjukkan apa-apa karena agent tidak pernah sampai.

Cara Kerja End-to-End

Alur 1 — pelanggan membayar lalu masuk

Langkah demi langkah
1. KASIR: Dashboard -> VOUCHER BARU -> pilih nominal -> "Buat Voucher"
2. BACKEND: validasi nominal (kelipatan 500)
            -> kode 6 digit acak (dicek unik)
            -> sisaWaktuDetik = floor(nominal / harga_per_menit * 60)
            -> password = "0000" (bcrypt)
            -> catat Transaction jenis BELI_BARU
            -> tampilkan kode + password ke kasir

3. KASIR: menulis kode di handout, memberitext ke pelanggan

4. PELANGGAN: mengetik kode + 0000 di layar kunci PC

5. OVERLAY: kirim client:login_request ke service lewat pipe

6. SERVICE: kirim client:login_request ke server

7. BACKEND: cek teknisi DULU (cegnah ada sesi teknisi)
            -> baru cari Account: kodeUnik dulu, lalu nama
            -> cek status ACTIVE
            -> cek sisa waktu > 0
            -> voucher: cek belum >30 hari tidak dipakai
            -> createSessionAndStart()
                 cek pc.rusak  (WAJIB sebelum lastUsedAt)
                 cek pc.autoUpdate
                 cek PC belum dipakai
                 cek akun belum dipakai di PC lain
            -> buat Session status BERJALAN
            -> set Pc.status = ACTIVE
            -> catat activity log + tulis berkas log billing
            -> kirim notifikasi FCM ke admin

8. BACKEND -> SERVICE: session:start { durasiDetikTersedia, account }

9. SERVICE: blokir Task Manager + screensaver, kirim ke overlay

10. OVERLAY: tampilkan mini panel, mulai hitung mundur

11. SETIAP DETIK: backend hitung ulang sisa waktu,
                 kirim session:tick ke overlay,
                 broadcast dashboard:pc_update ke kasir

Alur 2 — sesi berakhir

Tiga jalan keluar
A. WAKTU HABIS
   tick: sisa <= 0 -> stopSession("habis")
        -> Account.sisaWaktuDetik = 0  (voucher tidak bisa dipakai ulang)
        -> kirim session:stop

B. KASIR TEKAN KUNCI
   dashboard -> WS dashboard:lock_pc
   -> backend: unlockPc() -> stopSession("manual")
   -> SISA WAKTU DIKEMBALIKAN ke akun
   -> kirim admin:lock ke agent

C. PELANGGAN TEKAN STOP (di layar PC)
   overlay -> pipe StopSessionRequest
   -> service -> WS client:stop_session
   -> backend: unlockPc() -> stopSession("manual")
   -> SISA WAKTU DIKEMBALIKAN

SETIAP JALAN -> Pc.status = IDLE
             -> Pc.terakhirAktifAt = sekarang  (timer auto-matikan mulai ulang)
             -> catat activity log
             -> broadcast ke dashboard
Restart server tidak memutus sesi pelanggan Waktu terpakai dihitung ulang dari Session.waktuMulai + saldo di database, jadi penghitung di memori cuma pengirim. recoverRunningSessions() menyalakan ulang tick setelah restart, dan sudah terbukti dozens kali di log produksi tanpa ada detik yang hilang.

Alur 3 — mode teknisi

1. TEKNISI: klik teks "maintenance" di pojok kiri bawah
2. OVERLAY: buka dialog PIN
3. TEKNISI: masukkan PIN (atau minta OTP via Telegram)
4. OVERLAY -> pipe PinVerifyRequest -> SERVICE
5. SERVICE: coba hash bcrypt lokal, kalau gagal tanya server
6. SERVER: validasi PIN (atau kode OTP 6 digit, berlaku 5 menit)
7. BERHASIL:
     -> buat baris SesiTeknisi (selesaiAt = NULL)
     -> TIDAK buat baris Session
     -> TIDAK buat baris Transaction   <-- tidak masuk pendapatan
     -> kirim session:start dengan durasi 12 jam (hanya agar overlay terbuka)
8. TEKNISI: bekerja bebas di PC, tanpa penagihan
9. SELESAI: tekan STOP, atau matikan sakelar "Akses Teknisi" di Pengaturan

Alur 4 — pelanggan login, HP admin bunyi

1. Sesi mulai -> backend panggil kabarPemakaiNotifikasi()
2. Ambil semua token FCM milik user dengan role ADMIN
3. Kirim ke FCM, dengan nama member DISENSOR:
     "Budi Santoso" -> "bu***"
     kode voucher   -> "500344" (penuh, bukan kredensial)
4. Sumber ditulis supaya admin tahu:
     "Member bu*** - PC001 (PC)"         <- pelanggan di komputer
     "Member bu*** - PC003 (Dashboard)"  <- kasir tekan Start
     "Voucher 500344 - PC005 (Dashboard)" <- kasir buat voucher + Start
Nama member tidak boleh masuk notifikasi utuh Nama member adalah kredensial login-nya, dan notifikasi Android terlihat di layar kunci HP yang bisa dilihat siapa saja. Karena itu hanya dua karakter pertama yang dikirim. Kode voucher boleh penuh karena bukan kredensial.

Troubleshooting

Cara mencari penyebab dari gejala yang terlihat. Urutannya sengaja dari yang paling sering dan paling murah dicek.

Tiga keluhan yang pemetaannya TERBALIK dari penyebabnya Ini dicatat karena kesalahan menebak di sini mahal — gejalanya terlihat seperti fitur rusak, padahal masalahnya justru sebaliknya.
KeluhanPenyebab sebenarnya
“PC tidak auto-matikan lagi”Bukan fiturnya rusak. Ada SesiTeknisi menggantung, dan pengamannya menganggap “orang masih di depan PC” — selamanya.
“PC saya kenapa, mati sendiri”Bukan bug. Itu memang checkAutoShutdown yang bekerja. Cek terakhirAktifAt + auto_shutdown_menit.
“Kartu update nempel 100%, PC sudah bisa login”Kartu overlay yang lama tertinggal. State server sudah bersih; yang salah hanya tampilan.

Dua penyebab yang paling sering
  1. Error TypeScript yang tidak tertangkap test. Vitest hanya membuang tipe, jadi “Tests N passed” tidak berarti bisa dikompilasi. Lihat baris “Found N errors” dari watcher.

Perintah yang benar

Gejala: dashboard menggantung di “Menghubungkan…”

WebSocket lewat proxy Vite. Periksa /socket.io di vite.config.ts. Di produksi, periksa apakah ServeStaticModule mengecualikan /socket.io dan /session.

Gejala: clipboard gagal saat menyalin token

Clipboard API tidak jalan di HTTP biasa Halaman yang dibuka lewat http://192.168.x.x:3000 (non-secure) tidak punya navigator.clipboard, jadi pemanggilannya melempar TypeError dan selalu berakhir “Gagal menyalin”. Karena itu harus ada fallback document.execCommand('copy').

Gejala: update agent mandek di tengah unduhan

Pertama, cek apakah benar-benar mandek — heartbeat tetap hidup tiap 15 detik kan? Kalau iya, service-nya sehat dan yang bermasalah adalah kecepatan lewat Cloudflare Tunnel yang tidak stabil (terukur beda 50×: dari 2,9 MB/s sampai 56 KB/s pada jalur yang sama). Kalau kecepatan jatuh ke ~5 KB/s, berkas 89 MB memang tidak mungkin selesai dalam 15 menit — jadi ini bukan bug unduhan, batas waktunya bekerja benar.

Gejala: nama member terpotong di layar PC

Kolom kode di layar kunci maks 6 karakter (batas milik agent) dan kolom password maks 4 karakter. Akun dengan nama/kode lebih panjang tidak akan pernah bisa diketik sampai akhir. Server sudah menegakkan batas yang sama supaya akun yang tidak akan pernah bisa dipakai tidak ikut dibuat.
